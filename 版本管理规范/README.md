# 版本管理规范（个人迭代体系）

从单人项目实战中提炼的可复用迭代规范。目标：**可沉淀、可优化、有个人特点**——
每次项目迭代中发现更好的做法，就回流到这套规范里，让下一个项目直接受益。

## 文件清单

| 文件 | 职责 | 回答的问题 |
|------|------|-----------|
| `iteration-workflow.md` | 批次制开发流程 | 一批需求怎么从提出走到合入？ |
| `versioning.md` | 版本号与发版 | 版本号怎么定？怎么发版？怎么记录？ |
| `git-convention.md` | 提交与分支规范 | 提交信息怎么写？分支怎么命名？ |
| `templates/VERSIONING.md` | 项目版本记录模板 | 新项目直接复制改名的起点文件 |

三者的关系：

```
iteration-workflow.md（批次流程）
    ├─ 提交怎么写 → git-convention.md
    └─ 合并后怎么发版 → versioning.md
```

## 这套规范的三个个人特点

与通用模板的区别（也是提炼自实战的部分）：

1. **批次制**：迭代的基本单位是"批次"（一组相关改动），不是单个需求。
   一个批次一个分支、一次验收、一个合并点。
2. **实机验收门槛**：合并前必须用户验收（单人项目就是自己真机跑一遍），
   "代码写完了"≠"验证过了"≠"验收过了"。
3. **合并点/发版点分离**：merge 提交回答"这批改了什么"，release 提交+tag 回答
   "哪个版本包含它"。历史可回溯性靠这两个节点支撑。

## 新项目接入（3 步）

1. 复制 `templates/VERSIONING.md` 到项目根目录，改掉"当前版本"部分
2. 把三个规范文件放进团队/个人规范库（或项目 `docs/`），在 CLAUDE.md /
   助手系统提示中声明遵循
3. 第一个批次开始按流程跑，跑完回顾一次：哪里不顺就改规范文件

## 沉淀机制（规范怎么进化）

- **触发点**：迭代中任何"下次应该这样做"的念头，当场记到对应规范文件的末尾
  （草稿区），不靠事后回忆
- **节奏**：每个版本发版后花 5 分钟回顾：草稿区有没有该转正的条目？
  有没有实践打脸了规范的地方？
- **原则**：规范只收"被至少一个项目验证过的做法"，想法没落地前留在草稿区
- 规范文件本身建议用 git 管理（改动有历史，可回滚可对比）

## 正本与副本（规范文件的两处存放）

规范文件存在两处，**`D:\LvProject\版本管理规范` 是正本，项目内是副本**：

```
D:\LvProject\版本管理规范\     ← 正本（标准件，跨项目复用的源头）
<项目>\版本管理规范\           ← 副本（随项目仓库走，项目内可随时引用）
```

- **新项目接入**：从正本复制规范进项目（副本随项目 git 管理）
- **规范迭代永远发生在项目副本上**：因为规范条目必须"被至少一个项目
  验证过"才能沉淀，项目实战中发现的改进先改副本、随项目提交
- **验证有效后回写正本**：把副本中已验证的改动同步回正本，
  并用 `diff -r` 递归校验两处完全一致
- **同步方向单向**：项目 → 正本。不要在正本上直接改再拷进项目，
  否则规范改动失去项目实战背书

## 反馈回路（沉淀闭环）

```
① 项目实战 → 发现更好的做法（如发版产物归档 releases/）
      ↓
② 改项目内规范副本（随项目提交，有 git 历史背书）
      ↓
③ 验证有效 → 同步回正本（diff -r 校验一致）
      ↓
④ 下一个新项目启动 → 从正本复制规范进项目，直接受益
```

要点：**标准件只有一个**（正本）；**改动方向单向**（项目 → 正本）；
每次回写后两处必须完全一致，避免出现"两个版本的标准件"。
