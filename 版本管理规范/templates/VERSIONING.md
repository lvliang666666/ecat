## 2. 版本号规则（SemVer）

采用语义化版本：`主版本.次版本.修订号`（MAJOR.MINOR.PATCH）

| 位 | 何时递增 | 示例 |
|----|---------|------|
| 主版本 MAJOR | 不兼容的功能变更、数据结构破坏性迁移、UI 全面重做 | 1.0.0 → 2.0.0 |
| 次版本 MINOR | 向后兼容的新功能（新增页面、新增模块、新增设置项） | 1.0.0 → 1.1.0 |
| 修订号 PATCH | Bug 修复、样式微调、依赖升级、文档更新 | 1.0.0 → 1.0.1 |

规则：

- 版本号与版本声明文件保持同步（Flutter 为 `pubspec.yaml` 的 `version: x.y.z+构建号`，
  `+` 后为构建号，每次发版递增；其他技术栈替换为对应文件）
- 0.x 阶段允许随时破坏性变更，不遵循上述约束
- 一个批次对应一个版本号决策：全是修复 → PATCH；含新功能 → MINOR；含破坏性变更 → MAJOR

## 3. 提交信息规范（Conventional Commits）

格式：`<type>(<scope>): <subject>`

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 仅文档变更 |
| `style` | 不影响代码含义的格式调整 |
| `refactor` | 既非新增也非修复的代码变更 |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `chore` | 构建、依赖、配置等杂项 |
| `release` | 版本发布提交 |

- subject 一行以内，不加句号，中文英文均可
- scope 用模块名，前几个提交定下常用 scope 后保持一致
- 合并提交：`merge: 合并<批次主题>（一句话列要点）`
- 发版提交：`release: 发布 v<版本号>`

## 4. 分支策略（单人项目简化版）

- `main`：主分支，始终处于可构建、可发布状态，所有 tag 打在 main 上
- `feat/<主题>` / `fix/<主题>`：批次分支，验收通过后 `--no-ff` 合回 main 并删除
- 小改动（单文件、<20 行）直接提交 main，不强制开分支

## 5. Tag 与发布流程

Tag 命名：`v<版本号>`，打在 release 提交上。

发布一个新版本的步骤：

1. 确认验证全绿（静态检查零问题 + 全量测试通过）
2. 更新版本声明文件的版本号（构建号 +1）
3. 提交：`release: 发布 v<版本号>`（只含版本号变更）
4. 打 tag：`git tag -a v<版本号> -m "发布 v<版本号>"`
5. 构建产物并归档到项目根目录 `releases/`：
   - 命名：`<项目名>-v<版本号>-<平台>.<扩展名>`
     （如 `ecat-v1.3.0-android.apk`、`ecat-v1.3.0-windows.zip`）
   - `releases/` 加入 .gitignore（产物不进 git，可由 tag+源码复现）
   - 只归档与 tag 对应的正式发版产物，调试构建不放这里
