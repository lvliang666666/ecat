# 版本管理：版本号与发版

> 定义版本号规则、发版流程、版本记录沉淀。与 iteration-workflow.md（批次流程）、
> git-convention.md（提交格式）配合使用。

## 版本号规则（SemVer）

`主版本.次版本.修订号`（MAJOR.MINOR.PATCH）

| 位 | 何时递增 | 示例 |
|----|---------|------|
| 主版本 MAJOR | 不兼容变更：数据结构破坏性迁移、架构重做、UI 全面重做 | 1.0.0 → 2.0.0 |
| 次版本 MINOR | 向后兼容的新功能：新增页面/模块/设置项/成块的能力 | 1.0.0 → 1.1.0 |
| 修订号 PATCH | Bug 修复、样式微调、依赖升级、文档更新 | 1.0.0 → 1.0.1 |

规则：

- **一个批次对应一个版本号决策**：批次合并后，看这批改动的整体性质决定递增哪一位
  - 批次全是修复 → PATCH
  - 批次含新功能 → MINOR
  - 批次含破坏性变更 → MAJOR
- 0.x 阶段允许随时破坏性变更，不遵循上述约束（快速试错期）
- 版本号与项目清单文件保持同步（Flutter 是 `pubspec.yaml` 的 `version: x.y.z+构建号`，
  `+` 后构建号每次发版递增；其他技术栈对应各自的版本声明处）

## 发版流程（5 步）

1. **验证全绿**：静态检查零问题 + 全量测试通过（发版门槛，不可跳过）
2. **更新版本号**：改版本声明文件，构建号 +1
3. **发版提交**：`release: 发布 v<版本号>`（只含版本号变更，不夹带其他改动）
4. **打 tag**：`git tag -a v<版本号> -m "发布 v<版本号>"`（打在 release 提交上）
5. **构建产物并归档**：产物放入项目根目录的 `releases/`（见下节）

## 发版产物归档（releases/ 目录）

凡是有**安装包/可分发产物**的项目（移动端 APK/IPA、桌面端 EXE/MSI、
打包后的 Web 静态文件等），发版时统一归档到项目根目录的 `releases/`：

```
<项目根>/
└── releases/
    ├── ecat-v1.3.0-android.apk
    ├── ecat-v1.3.0-windows.zip
    └── ...
```

规则：

- **命名**：`<项目名>-v<版本号>-<平台>.<扩展名>`，平台小写
  （`android` / `windows` / `macos` / `linux` / `web`）
- **一个版本多个平台**：同名不同平台后缀，都放同一个 `releases/`
- **目录加入 .gitignore**：产物不进 git（体积大且可由 tag+源码复现），
  归档价值在本地留存与回滚验证
- **只放正式发版产物**：日常调试构建（`build/` 里的中间产物）不放这里；
  验收用的临时包直接从 `build/` 取，验收通过、发版后才归档进 `releases/`
- **产物必须与 tag 对应**：`releases/` 里的文件由打完 tag 的提交构建而来，
  不归档"版本号对不上"的包

为什么固定目录而不是散放：

- 找"上一个能用的版本"时只有一个地方可看
- 版本号在文件名里，与 tag 一一对应，回滚验证直接取文件安装
- 避免把旧包遗留在项目根目录/下载目录里分不清新旧

## 合并点与发版点分离

一个批次合入后，main 上会出现两个相邻节点，职责不同：

```
* bf9abe4 (tag: v1.1.0) release: 发布 v1.1.0   ← 发版点：版本号+tag 在这
*   332cac5 merge: 合并第一批小bug修复（…）      ← 合并点：批次改动边界在这
|\
```

- **合并点**回答"这批改了什么"（看 merge 提交的说明和 diff）
- **发版点**回答"哪个版本包含它"（看 tag）
- 两者分开的原因：合并后可能还有收尾改动（版本号、文档）才发版；
  也可能合并多个批次才发一次版。混在一个提交里，两个问题都答不清

## 版本记录沉淀

每个项目维护一份版本记录（如 VERSIONING.md），三部分：

1. **当前版本**：版本号 + 日期 + 本版新增/变更清单（用户视角描述，不写实现细节）
2. **版本号规则**：本文的 SemVer 表（直接复制）
3. **历史版本表**：`| 版本 | 日期 | 说明 |`，一行一版，说明一句话

写法要求：

- 变更清单写**用户能感知的东西**（"进会话直达最新消息"），不写代码结构（"改用 reverse ListView"）
- 每次发版时同步更新，不发版不更新
- 这份记录是 CHANGELOG 的雏形：项目对外发布时可直接衍生 CHANGELOG.md

## 反模式（禁止）

- ❌ 发版提交里夹带功能改动（release 提交只动版本号）
- ❌ tag 打在功能提交上（tag 永远打在 release 提交）
- ❌ 版本记录写实现细节（用户视角，不是开发者视角）
- ❌ 凭感觉定版本号（对照 SemVer 表：有没有新功能？有没有破坏兼容？）
- ❌ 连续合并多个批次不发版（版本粒度失控，出问题无法定位到版本）
- ❌ 产物散放（根目录/下载目录/聊天工具里各一份，分不清哪个对应哪个版本）
- ❌ 把产物提交进 git（体积大、可复现，.gitignore 掉 `releases/`）
