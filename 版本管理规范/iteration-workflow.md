# 迭代工作流：批次制开发

> 从单人项目实战中提炼的核心流程。定义"一批需求"从提出到合入的完整生命周期。
> 与 versioning.md（版本号）、git-convention.md（提交格式）配合使用。

## 核心理念：批次（Batch）

**批次是迭代的基本单位**：一组相关联的需求/修复，在同一个分支上开发、
一起验证、一起合并、一起发版。

为什么用批次而不是"一个需求一个分支"：

- 单人项目开太多分支是纯管理开销，没有协作收益
- 用户提需求时经常一口气提 4~5 个相关小改动（"这几个一起修复"），天然就是一批
- 批次合并 = 一个清晰的合并点，回溯"哪批改动是一起的"一目了然

## 批次生命周期

```
收集需求 → 复述确认 → 建批次分支 → 逐项实现+验证
    → 批次内全量验证 → 用户验收 → 合并 main → 发版（可选）
```

### 1. 收集与确认

- 用户连续提出多个改动时，先复述全部条目，确认无遗漏再开工
- 判断是否同批：改动是否围绕同一主题（如"第一批小bug修复"全是体验问题）
  - 同主题 → 一个批次分支
  - 明显独立的大功能 → 各自开分支，不硬凑
- 有争议的条目（方案不唯一）先确认方案，再进批次

### 2. 批次分支

- 命名：`feat/<主题名>` 或 `fix/<主题名>`，主题名用批次目标而非条目堆砌
  - ✅ `feat/agent-and-file-export`（两个主题也可用 and 连接）
  - ✅ 第一批小bug修复 → 分支名体现主题
  - ❌ `fix/bug1-bug2-bug3-bug4`（条目堆砌，无主题）
- 批次内所有提交都在该分支上，main 保持稳定

### 3. 逐项实现

- 按条目逐个实现，每项独立提交（一个提交一件事）
- 每项改完立即验证（编译/lint/测试），失败修到通过才做下一项
- 用户中途追加需求：同主题的追加进当前批次；不同主题的记入下一批次，不混入

### 4. 批次验证与验收

批次内全部条目完成后：

1. **全量验证**：analyze 零问题 + 全量测试通过（标准见 code-discipline）
2. **用户验收**：把批次改动清单报给用户，明确说"验证通过，可以合并吗？"
   - 单人项目里"用户验收"常常就是自己真机跑一遍——不要省略，模拟器和真机是两回事
3. **验收通过才合并**。验收发现问题的，修完重新验证再验收

### 5. 合并

- `git checkout main && git merge --no-ff <批次分支>`
- `--no-ff` 保留合并点：批次内提交再多，main 上只有一个节点代表"这批改动"
- 合并后删除批次分支
- 合并 ≠ 发版：合并只是代码进 main，发版是独立动作（见 versioning.md）

## 批次粒度参考

| 批次规模 | 判断 |
|---------|------|
| 1~3 个小改动 | 可以不开分支，直接提交 main（小改动例外） |
| 4~10 个相关改动 | 典型批次，开分支 |
| 超过 10 个或含大功能 | 拆成多个批次，先做依赖链最底层的 |

## 反模式（禁止）

- ❌ 不经验收直接合并（"代码写完了"不等于"验证过了"更不等于"验收过了"）
- ❌ 批次里混入无关改动（顺手格式化别的文件——要么单独提交，要么别做）
- ❌ 批次无限膨胀（用户不断追加，批次永远合不了——同主题追加可以，新主题开新批）
- ❌ 用 fast-forward 合并（丢失批次边界，历史变成一条无法回溯的直线）
- ❌ 合并完不删分支（僵尸分支堆积，下次还得分心判断它死没死）
